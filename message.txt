Regras que valem para todos:

Quem fez a ação não recebe o próprio aviso.
Quem recebe é calculado no backend, a partir da igreja do recurso.
Um aviso que falha nunca derruba a ação principal.
Backend
1. Migration e schema


model Notification {
  id        String    @id @default(uuid())
  userId    String
  churchId  String?
  tipo      NotificationType   // os 5 da tabela acima
  titulo    String
  texto     String
  link      String
  chave     String    // ex.: "evento:<id>", evita aviso repetido
  lidaEm    DateTime?
  emailEm   DateTime? // null = e-mail ainda não enviado
  criadaEm  DateTime  @default(now())
  @@unique([userId, chave])
  @@index([userId, lidaEm])
  @@index([emailEm])
}
Mais um campo User.emailNotificacoes Boolean @default(true), para a pessoa poder desligar o e-mail.

A chave única, com createMany({ skipDuplicates }), resolve o caso de um evento desativado e reativado: o aviso não sai de novo.

2. Módulo src/notificacoes/

NotificacoesService.notificar(userIds, aviso): grava uma linha por pessoa, sem a que fez a ação, e engole e registra o erro se falhar.
Funções auxiliares adminsDaIgreja(churchId) (pelos churchRoles com ADMIN) e membrosDaIgreja(churchId) (pelo memberChurchId).
Endpoints, todos só com o usuário logado e sempre filtrando por userId:
GET /notificacoes?antes=<data>: 20 por página, mais o total de não lidas;
GET /notificacoes/nao-lidas: só o número, para o sino perguntar barato;
PATCH /notificacoes/:id/lida: se o id for de outra pessoa, devolve 404;
PATCH /notificacoes/lidas: marca todas.
3. E-mail pelo cron, sem fila

A cada 5 minutos, o cron busca os avisos com emailEm = null de quem tem emailNotificacoes ligado.
Agrupa por pessoa: um e-mail "Você tem 3 avisos" com a lista e os links, e não 3 e-mails separados.
Antes de enviar, grava emailEm, de modo que só uma passada do cron pega cada aviso (updateMany ... where emailEm null). Se o envio falhar, volta para null.
Usa o mail.service atual: o desvio em ambiente de desenvolvimento e a logo continuam valendo. O rodapé do e-mail leva ao lugar onde se desliga o envio.
Aviso com mais de 1 dia que ainda não saiu por e-mail não sai mais, para não mandar coisa velha depois de uma queda.
4. Limpeza: um cron diário apaga as notificações lidas com mais de 90 dias e as não lidas com mais de 180.

5. Testes

Quem recebe cada aviso: só os admins daquela igreja, e nunca quem fez a ação.
A chave impede aviso repetido.
Ninguém lê nem marca a notificação de outra pessoa.
O cron agrupa por pessoa e não envia o mesmo aviso duas vezes.
Front
src/features/notificacoes/, com api.ts, types.ts e components/sino.tsx:
O sino fica na barra do topo, com o número de não lidas. Pergunta à API a cada 60s e quando a aba volta a ficar em foco.
Ao clicar, abre uma lista com o ícone e a cor do módulo de cada aviso, título, texto, há quanto tempo, um ponto nos não lidos e "Marcar todas como lidas".
Ao clicar num aviso: marca como lido, troca a igreja escolhida para a do aviso (setEscolhida) e abre o link.
Sem avisos: "Nenhum aviso por aqui".
Configurações / perfil: uma chave "Receber avisos por e-mail".

Decisões que deixei num padrão (diga se quiser outro)
Novo evento vai só para os membros da igreja. Mandar para todo mundo que já se inscreveu em algum evento dela aumenta muito o volume.
E-mail agrupado a cada 5 minutos. A alternativa é um resumo diário.
Uma chave só para desligar o e-mail. Escolher tipo a tipo fica para quando alguém pedir.
Fora deste plano, de propósito: tempo real por socket e push no celular. O sino com a pergunta a cada 60s cobre o caso por enquanto, e dá para acrescentar os dois depois sem mudar a tabela.
